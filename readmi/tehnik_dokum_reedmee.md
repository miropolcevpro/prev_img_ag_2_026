# Техническая документация и инструкция
## Инструмент обновления прайса для Tilda‑конфигуратора (prev_img_ag_2_026)

Дата: 2026‑02‑26  
Репозиторий: `miropolcevpro/prev_img_ag_2_026`  
Цель: обновлять `price_catalog.json` из XLSX производителя **быстро, повторяемо и без риска поломок**.

---

## 1) Что это за инструмент

Это пайплайн «сырой прайс производителя → валидированный JSON прайс для конфигуратора».

Компоненты:
1. **Исходный прайс производителя (XLSX)**  
   Хранится в репозитории как единственный источник данных:  
   `source/price_supplier.xlsx`

2. **Конвертер/валидатор**  
   Скрипт, который читает XLSX и обновляет значения в `price_catalog.json`, **сохраняя структуру JSON**:  
   `price_update_tool/update_price_catalog.py`

3. **GitHub Actions workflow («одна кнопка»)**  
   Автоматически запускает конвертер и создаёт Pull Request с обновлённым `price_catalog.json`:  
   `.github/workflows/update-price.yml`

4. **Отчёт обновления**  
   Генерируется при запуске:  
   `price_update_report.json`  
   Также прикладывается как artifact в GitHub Actions (zip с отчётом).

---

## 2) Как это связано с Tilda и конфигуратором

### 2.1. Где используется прайс
Tilda‑конфигуратор (HTML‑snippet) не хранит цены внутри себя. Он загружает данные из репозитория/веб‑хостинга (GitHub Pages/jsDelivr и т.п.) в формате JSON.

Ключевой файл:
- `price_catalog.json` — **единственный файл прайса**, который читает конфигуратор.

После обновления `price_catalog.json` в репозитории конфигуратор начнёт использовать новые значения при следующей загрузке данных (зависит от CDN/кэша).

### 2.2. Про кэш (важно)
Если конфигуратор использует CDN (например jsDelivr) — обновления могут приходить с задержкой из‑за кэширования.
Рекомендуется (если у вас включён version‑busting):
- повышать `ASSET_VER` / параметр версии, который добавляется к URL JSON (например `?v=...`), чтобы браузер/CDN точно взяли новую версию.

Если version‑busting у вас реализован в коде конфигуратора через `ASSET_VER`, то после обновления прайса:
- либо обновляйте `ASSET_VER` (рекомендуется),
- либо очищайте кэш/ждите обновления CDN.

## 3) Что именно обновляется в `price_catalog.json`

Скрипт **не меняет схему** `price_catalog.json`. Он обновляет только значения внутри существующих объектов:

### 3.1. Плитка (pavers)
- цены по колонкам/ключам:
  - `grey`
  - `mono_color1`
  - `mono_color2`
  - `colormix_2`
  - `colormix_3`
  - `colormix_fakt`
  - `stonemix`
- упаковка/вес (если присутствуют в прайсе):
  - `pcs_per_pallet`
  - `pcs_per_m2`
  - `m2_per_pallet`
  - `pallet_weight_kg`
- значения могут быть:
  - числом (float/int)
  - строкой `"по запросу"` (допускается)

### 3.2. Бордюр (curbstone)
- цены по тем же ключам
- упаковка/вес:
  - `pcs_per_pallet`
  - `pallet_weight_kg`
  - при необходимости могут дополняться производные поля (если в вашем JSON они предусмотрены)

## 4) Валидации (защита от поломок)

Скрипт работает в режиме **fail‑fast**:
- если не удаётся сопоставить строки XLSX с позициями в `price_catalog.json`,
- если отсутствуют обязательные колонки,
- если получаются некорректные значения (пусто там, где должно быть число/«по запросу»),

то выполнение завершается ошибкой, workflow падает, **PR не создаётся**.

Это гарантирует, что в `main` не попадёт «битый» прайс.

## 5) Как обновлять прайс (основной сценарий)

### 5.1. «Одна кнопка» через GitHub Actions (рекомендуется)
1. Получите новый XLSX от производителя.
2. Переименуйте файл в `price_supplier.xlsx`.
3. Замените файл в репозитории по пути:
   - `source/price_supplier.xlsx`
4. Сделайте commit и push в `main`.
5. Откройте GitHub → вкладка **Actions** → workflow  
   **Update price_catalog.json from supplier XLSX**
6. Дождитесь успешного запуска workflow.
7. Перейдите во вкладку **Pull requests** и откройте PR  
   **Update price_catalog.json (auto)**
8. Проверьте изменения:
   - вкладка **Files changed** (изменения в `price_catalog.json`)
9. (Опционально) скачайте `price_update_report` из run → **Artifacts**.
10. Нажмите **Merge pull request**.

После merge в `main` будет обновлён `price_catalog.json`.

### 5.2. Если PR пустой
Если вы заменили XLSX на тот же самый (значения не изменились), PR может быть пустым (нет diff). Это нормальное поведение: прайс не поменялся.

## 6) Ручной запуск (локально) — для проверки перед пушем

Из корня репозитория:

```bash
python3 price_update_tool/update_price_catalog.py   --xlsx "source/price_supplier.xlsx"   --price-catalog "./price_catalog.json"   --report "./price_update_report.json"
```

Далее проверьте:

```bash
git diff -- price_catalog.json
```

- если diff есть — прайс обновился
- если diff пустой — изменения отсутствуют

## 7) Что делать, если workflow упал

Откройте GitHub → **Actions** → последний run workflow → шаг  
**Run price update + validation**.

Типовые причины:
- производитель изменил названия позиций/форматов;
- поменялись заголовки колонок в XLSX;
- появились новые позиции, которых нет в JSON;
- изменился лист/структура XLSX.

Решение:
- смотреть `price_update_report.json` (artifact) и список не‑сопоставленных позиций;
- обновить маппинг в `update_price_catalog.py` (точечный патч);
- повторить запуск.

## 8) Где находятся файлы и что коммитить

### В репозитории хранятся:
- `source/price_supplier.xlsx` — сырой прайс производителя
- `price_catalog.json` — рабочий прайс для конфигуратора
- `price_update_tool/update_price_catalog.py` — конвертер/валидатор
- `.github/workflows/update-price.yml` — автоматизация

### При обновлении прайса обычно меняются:
- `source/price_supplier.xlsx` (в `main`, чтобы workflow запустился)
- `price_catalog.json` (в PR, который создаёт workflow)

Рекомендуемая практика:
- `main`: коммитим только новый XLSX
- PR: workflow коммитит обновлённый `price_catalog.json`, вы мержите PR

## 10) Примечания по соответствию «всегда считалось без ошибок»
- Конфигуратор зависит от **структуры** `price_catalog.json`. Поэтому мы не генерируем новый JSON, а обновляем существующий.
- Любые несовпадения/пропуски ловятся валидациями — лучше остановить релиз, чем получить неверный расчёт на сайте.
